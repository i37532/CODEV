## 数学接口与代码范围

新增的 [StaVelocityControl.hpp](../../../src/modules/mc_pos_control/PositionControl/StaVelocityControl.hpp)
和 `.cpp` 为独立 C++14 内核，三轴状态各自保存 `nu`，无共享积分。

```text
s = v - v_sp                                  [m/s]
a_sta = -lambda1 sqrt(|s|) sign(s) + nu_k     [m/s^2]
nu_next = nu_k - h lambda2 sign(s)            [m/s^2]
```

`lambda1` 的单位是 `(m/s²)/sqrt(m/s)`，`lambda2` 为 `m/s³`。`evaluate()` 只给出候选，
使用旧 `nu_k`；`commit()` 才且仅可一次写入 `nu_next`。候选在 reset、参数变更或先前
commit 后会被拒绝为 stale，因而同一采样不能无意重复积分。

该内核的输出仅是 `a_sta` 加速度纠偏：没有 `g`、力矩归一化、质量除法、推力、姿态、限幅或
保护逻辑。将来适配层只能按 `a_req=a_sta+a_ff` 加入现有加速度前馈一次；V02 的测试覆盖了
该一次相加，但尚未实现生产适配层。把纯核看作 `g=1` 仅是**没有输入增益映射的接口恒等**，
不是对真实姿态/电机/内环响应无滞后的证明。

为使“不可生效”可审查，内核库只在 `BUILD_TESTING` 下构建，不属于生产 `PositionControl`
目标；`PositionControl.cpp`、其 dispatcher、参数、日志、PID 数学、位置 P、Z 速度 PID、
姿态和角速度控制均未改。V01 selector 仍把 MODE=1/AXES=1 拒绝为 mode-unimplemented +
axes-unavailable。默认 SITL 固件的 `nm -C` 查询没有 `StaVelocityControl` 符号。

## 测试与结果

新增 `unit-StaVelocityControl` 共 **7** 个实际 C++ 用例，均通过：

1. 旧 `nu` 输出、一次 commit 与非零 `a_ff` 的一次相加；
2. 正/负对称和零误差保留非零 `nu`；
3. 三轴/实例隔离、reset、参数更新后的陈旧候选和重复 commit；
4. 非法轴、未配置、无效 dt/参数/输入、溢出与中间下溢均保持状态原子性；
5. 384 步 8/12 ms 冻结序列，与独立 binary64 ESTA 参考逐步比较；
6. 独立 ZOH 对象：常量扰动、变化速度目标、非零前馈，以及单独的斜坡扰动/饱和/滞后对象；
7. MODE=1/AXES=1 仍无法成为有效速度控制器。

双精度参考只实现标量公式和自身对象状态，不调用生产 `evaluate/commit`。它与实时 float
接口的比较采用 float-vs-double 容差；受饱和/滞后对象只验证数值有限及约束发生，**不**把
保护后输出称为理想 STA 方程的严格解，也不据此宣传飞行性能。

回归实际运行的既有目标也全部通过：`VelocityControl` 6、`PositionControl` 15、`ControlMath`
9、`Takeoff` 8、`RateControl` 1、`RateControlDispatcher` 4、`StaRateControl` 11，共 54 个
既有指定 C++ 用例；连同新增 7 个为 **61 个指定 C++ 用例**。`RateControl` 筛选命令还运行了
2 个现有 ISTA/Proper-ISTA 测试目标，均通过，但不计作本阶段速度 ESTA 验收数量。

开发中保留以下失败事实：首次新增测试有一个 C++14 初始化列表推导错误，随后有一个
`-Wfloat-equal` 错误，均在测试代码中修正；第一次对象比较因把 double 对象状态传给 float
内核而使用过紧容差，调整为明确的 float-vs-double 容差后通过。另一次合并正则筛选命令未转义
shell 的 `|`，没有执行有效测试；一次系统 Python 构建因缺少 `toml`、`empy` 失败。最终所有
实际验证均使用项目 `.px4-python` 环境。上述都没有启动 SITL 或飞行。
